1. 三层分工总览

怎么读这张图：OMPI 只是把 MPI API 交给 UCP；UCP 负责协议决策；obmm UCT 负责把一个 AM fragment 真正落到 peer_ctl / peer_elems / peer_descs 指向的共享内存里。

2. 建链流程图：消息发送前，obmm 先做了什么

这张图对应 obmm_sysfs.c、obmm_md.c、obmm_iface.c:317-457、 obmm_ep.c:26-133。真正值得记住的是：发送时能直接操作 peer slot， 是因为这些“找 region / 找 slot / 校验 geometry”的事都在建链阶段提前做完了。

3. obmm_pool 在 region 里的位置：它不是“附属结构”，而是整个数据面的地基

这张图想解决的误区：之前那些 send/recv 图默认你已经“拿到了一个 slot”。 但 slot 从哪里来、为什么能跨进程安全复用、为什么 stale 写能被丢弃，这些都不是 obmm_ep.c 解决的， 而是 obmm_pool.c 在 region 头部做掉的。

4. obmm_pool attach / open 状态机：本地 iface 创建和 peer ep_create 走的是两条不同路径

最容易忽略的点：attach 和 open 不是一回事。
attach 是“我要在本地 export region 上拥有并初始化这个 pool”；
open 是“我只是个 sender，要读 peer 已经建好的 pool，找到它的 slot”。
这也是为什么 iface 创建 和 ep_create 对 obmm_pool 的使用是完全不同的。
额外要记住：initializer_pid / initializer_starttime 不是装饰字段， 它们是 dead-initializer recovery 的依据；否则一个崩掉的初始化者会把整个 pool 永久卡在 INITING。

5. obmm_pool slot 生命周期：alloc / scavenge / free / generation 是怎样串起来的

这部分和 send/recv 代码是强耦合的：obmm_pool_free_slot() 里先 bump generation， 不是“多做了一步保险”，而是为了让 obmm_iface_progress() 能识别 stale write。
也就是说：obmm_pool.c 决定 slot 生命周期，obmm_iface.c 在接收时真正执行“按 generation 丢弃旧消息”。

6. V2 slot 内部布局图：short 和 bcopy 为什么会走不同数据区

对照代码：obmm_fifo.h:63-122、obmm_ep.c:298-327、obmm_iface.c:254-263、 DESIGN.md:137-198。short 和 bcopy 的差别主要不在控制流，而在 payload 落点： short 在 elem+1，bcopy 在 desc[N]。

7. am_short 时序图：64B / 2032B 这类小消息怎么跑

对照代码：pml_ucx.c:1022-1060、tag_send.c:150-177、 obmm_ep.c:174-241、obmm_iface.c:221-295、 eager_rcv.c:138-147。short 的关键记忆点：UCP 的 tag 作为 8B header 下推； obmm short 真正写的是 [header][payload] 到 FIFO elem body。

8. am_bcopy 时序图：2033B / 4096B 这类消息怎么走到 paired-desc

对照代码：eager_snd.c:130-146、proto_am.inl:75-98、 obmm_ep.c:273-331、obmm_iface.c:254-283、DESIGN.md:290-307。 V2 最值得反复看的一点：am_bcopy 的 payload 不在 FIFO elem 里，而在同编号的 desc[N] 里；receiver 只在 callback 生命周期内使用它。

9. UCP 协议选择图：为什么 64KiB / 1MiB 不是 obmm 新增很多发送接口

small eager short

典型入口：tag_send.c:150-177。够小就直接下推 uct_ep_am_short。

single-frag bcopy

典型入口：eager_snd.c:130-146。一次 uct_ep_am_bcopy 就够。

multi-frag bcopy

典型入口：proto_am.inl:120-198。UCP 多次调用同一个 obmm bcopy primitive。

rendezvous

典型入口：rndv.c:1828-1852。是否会走到 rkey_ptr，取决于 MD 能力声明。

10. 背压 / pending 图：为什么高并发时不能只盯着 am_short / am_bcopy

关键代码：obmm_ep.c:352-407、obmm_iface.c:286-293。如果只盯着 uct_obmm_ep_am_short() / uct_obmm_ep_am_bcopy()，很容易看不出为什么 mpi_bw_v2.c / osu_bibw 这类场景会卡在背压恢复上。

最后怎么配合 Markdown 版一起读

  1. 先打开这份 HTML，把整体路径和 slot / desc 的直觉建起来。
  2. 再回到 V2_IMPLEMENTATION_WALKTHROUGH.md，按里面的路径 A / B / C 顺序逐文件追代码。
  3. 真正遇到“注释和代码像是不一致”的地方，优先相信 obmm_*.c/.h 的当前实现。
